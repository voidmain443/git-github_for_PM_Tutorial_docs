# 01. 프로젝트 착수

윤서진이 “왜 시작하고 어디까지 할지, 당신에게 어떤 권한이 필요한지 한 문서로 정리해 주세요”라고 요청합니다. 여러분은 PM 한지우입니다.

프로젝트 헌장(Project Charter)은 사업을 시작할 이유와 PM의 권한을 공식화합니다. 스폰서는 자금과 중요한 의사결정을 책임지는 사람입니다. 헌장의 목표는 달성할 결과이고, 범위는 제공할 것의 경계입니다. 인수는 현업이 결과를 받아들이는 결정, 종료는 남은 책임까지 정리한 뒤 프로젝트를 마치는 결정입니다. 상세 계획을 아직 모른다는 이유로 착수에 필요한 목적과 권한까지 비워 두지 않습니다.

이 단원은 설명 → 자료 조회 → 예제 → 직접 확인 → 검토·수정 → 다음 업무 순서로 진행합니다. 웹 입력은 필요하지 않습니다. 문서를 작성할 때는 양식을 내려받고 같은 문서의 버전을 이어 갑니다.

## 단원 본문: 업무를 차례로 이해하기

사업을 시작할 이유와 권한을 헌장으로 연결하고 검토·수정·승인의 차이를 이해한다.

가져올 것: 업무 파악 메모에서 사업 필요와 자료 위치를 다시 찾는다. / 문서 작성자·검토자·승인권자를 구분한다. / 헌장·가정 로그·이해관계자 등록부 양식을 준비한다.

마치면 할 수 있는 일: 목표·경계·자금 상태·권한을 근거 있는 문장으로 쓴다. / 역할별 검토 의견에 따라 초안의 판단 조건을 보완한다. / 수정본을 승인 조건과 대조하고 이후 계획의 입력으로 넘긴다.

### 1. 지금 필요한 것은 상세 일정표보다 시작의 합의입니다 (S0)

업무를 파악한 여러분에게 이제 프로젝트 헌장 D01을 준비하는 일이 남았습니다. 헌장은 앞으로 모든 일을 어떻게 할지 적는 상세 계획이 아닙니다. 왜 이 사업을 시작하는지, 무엇을 바꾸고 무엇을 바꾸지 않을지, 어떤 조건으로 성공을 판단할지, PM이 어떤 권한으로 일을 진행할지를 스폰서가 결정할 수 있게 묶습니다.

정산팀의 불편을 들으면 곧바로 개발 업무를 나누고 싶은 마음이 들 수 있습니다. 그러나 목표가 “빨라지는 것”인지 “처리 이력이 남는 것”인지, 기존 포털을 시험하는지 새로 만드는지, 자금 한도가 확정 예산인지가 합의되지 않으면 상세 계획을 정교하게 만들어도 서로 다른 사업을 계획할 수 있습니다. 헌장은 이 해석의 차이를 초기에 줄이는 문서입니다.

이번 사업은 기존 결제·정산 운영을 유지하면서 내부 업무 도구를 개선합니다. S01의 요청을 출발점으로 삼되 업무의 구체적 뜻은 S03과 S17을 함께 읽습니다. 예를 들어 “가맹점”이라는 단어가 나온다고 신규 가맹점 앱을 만들겠다는 약속으로 넓히면 안 됩니다. 헌장 작성자는 짧은 사업 제안과 상세 확인 회신을 연결해야 합니다.

| 지금 작성할 것 | 그 항목이 돕는 결정 |
|---|---|
| 사업 필요와 목표 | 이 사업을 시작할 이유가 있는가 |
| 상위 요구와 포함·제외 경계 | 무엇을 인도하는 사업인가 |
| 자금 한도와 주요 일정 | 어떤 제약 안에서 계획해야 하는가 |
| PM 권한과 승인 경로 | 누가 무엇을 결정할 수 있는가 |
| 가정·위험·종료 책임 | 무엇을 더 확인하고 어디까지 책임지는가 |

먼저 D01을 v0.1 초안으로 준비합니다. 프로젝트 ID, 작성자, 문서 상태를 표시한 뒤 본문을 씁니다. 지금은 S0이므로 승인번호와 승인일을 만들지 않습니다. 자료의 작성자가 스폰서라고 해도 그 원천자료를 읽었다는 사실이 학생의 D01을 승인한 사건은 아닙니다.

이 단원의 흐름은 초안→역할별 검토→수정본→승인 조건 대조입니다. 처음부터 완벽한 문장을 만들기보다 한 항목에 필요한 사실과 판단을 구분해 적습니다. 그 다음 빠진 조건을 찾아 보완하는 과정을 경험해야 실무에서 회신을 받고 문서를 수정하는 이유를 이해할 수 있습니다.

### 2. 좋은 헌장은 명확한 목표와 정직한 미확정을 담습니다 (S0)

헌장의 목표는 “개선한다”라는 동사에 멈추지 않습니다. 무엇을, 어떤 기준으로, 어느 기간에, 누가 확인하는지 있어야 합니다. 목표 수치만 맞아도 측정 대상이 다르면 다른 약속이 됩니다. 팀의 대사 경과시간과 직원별 공수, 오픈 직후 관찰값과 정해진 기간의 평균은 같은 지표가 아닙니다.

성공 조건을 자세히 적는 것과 미래 결과를 미리 적는 것도 구분합니다. “평균이 기준 이내인지 측정한다”는 목표 정의이고 “기준을 달성했다”는 실적 보고입니다. 지금은 결과가 나오기 전입니다. 이후 상세 시험을 어떻게 할지는 요구사항과 품질계획에서 구체화하므로 헌장에는 상위 결과와 확인 책임을 분명히 두면 됩니다.

자금에서도 한도·기준선·실적의 상태를 나눕니다. S17은 사업 자금이 계획을 검토할 투자 한도이며 상세 원가기준선은 별도 승인한다고 설명합니다. 회사 현금을 근거로 PM의 사용권한을 확대해서는 안 됩니다. 일정 역시 스폰서가 제시한 종료 목표와 활동을 계산한 상세 일정은 다릅니다. 목표를 알고 있다는 것만으로 실현 가능성이 검증된 것은 아닙니다.

| 헌장에 적는 정보 | 주의할 구분 |
|---|---|
| 목표 | 측정 계획과 실제 달성 결과 |
| 범위 | 기존 포털 공유권한 시험과 신규 화면 개발 |
| 자금 | 투자 한도와 상세 승인 기준선 |
| 권한 | 일상 업무 배정과 기준선 변경 승인 |
| 종료 | 현업 인수·프로젝트 종료 승인·사후 편익 측정 |

가정은 계획할 때 참이라고 두는 전제, 제약은 지켜야 할 경계, 위험은 아직 발생하지 않은 사건이 목표에 영향을 줄 가능성입니다. 한 표에 “주의사항”으로 합치면 각각 무엇을 확인해야 하는지 사라집니다. A01에는 전제의 확인 근거와 책임을, 헌장에는 중요한 요약과 영향 문서를 연결합니다.

명확하지 않은 부분을 임의로 확정하는 것보다 계획 단계에서 누가 무엇을 확인할지 적는 편이 좋은 관리입니다. 다만 자료에 이미 답이 있는데도 무조건 미정으로 남기는 것은 다릅니다. S17의 고정 회신처럼 현재 제공된 사실은 사용하고, 실제로 아직 없는 상세 배정·실적·승인만 미확정으로 구분해야 합니다.

### 3. 헌장의 항목 순서대로 원천을 읽습니다 (S0)

모든 문서를 처음부터 끝까지 여러 번 읽기보다 헌장의 빈 항목을 질문으로 바꿔 읽습니다. 사업 필요에는 S01과 S05를 함께 사용합니다. S01은 왜 개선하려는지 설명하고 S05는 그 문제가 현재 업무 흐름의 어디에 나타나는지 보여 줍니다. “좋은 시스템을 만든다”를 쓰기 전에 누구의 어떤 일이 달라지는지 표시하세요.

목표에는 S01의 현재값과 목표값, S17의 측정 정의를 연결합니다. 원천 숫자를 하나씩 옮기기 전에 팀 경과시간·측정 기간·담당자의 말이 어느 문서에 있는지 확인합니다. 측정 조건을 빠뜨리면 운영자가 나중에 어떤 기록을 모아야 할지 알 수 없습니다. 계획된 편익을 이미 생긴 현금 절감으로 표현하지 않는 것도 이 읽기 단계에서 점검합니다.

상위 요구와 범위는 S03을 기준으로 S17의 포털 경계를 대조합니다. 요구 ID는 후속 문서와 연결할 표시이므로 기능 설명과 함께 보존합니다. 정산금 계산이 맞는 것, 대사 분류가 맞는 것, 예외 정보가 남는 것, 권한이 지켜지는 것, 운영자가 사용할 수 있는 것은 다른 조건입니다. 하나의 “정확도”로 합치지 않습니다.

| 헌장 질문 | 우선 원천 | 함께 확인할 원천 |
|---|---|---|
| 왜 시작하는가 | S01 | S05 업무 흐름·교훈 |
| 성공을 언제 어떻게 판단하는가 | S17 | S01 목표 |
| 무엇을 포함·제외하는가 | S03 | S17 기존 포털 경계 |
| 자금과 권한은 어디까지인가 | S01, S02 | S04, S17 |
| 종료와 편익 책임은 무엇인가 | S17 | S05 교훈 |

사람은 D30에서 이름·역할·권한·관심·확인할 일을 정리합니다. 박다은에게 업무 인수, 오수빈에게 보안, 정유나에게 시험 증거, 윤서진에게 헌장과 기준선 승인을 연결합니다. 영향력에 관한 학생 판단과 회사가 정한 권한을 서로 다른 성격으로 표시하세요. 중요한 사람이라는 이유로 모든 문서의 승인자로 적지 않습니다.

ERP에서는 원천 문서 ID를 찾고, 필요한 경우 조직·담당자 상세로 확인 책임을 대조합니다. 0건이 나오면 아직 공개되지 않은 승인 자료를 열기보다 현재 단계와 검색조건부터 확인합니다. 초안에 필요한 사실은 S0 안에서 찾습니다. 승인 결과는 초안·검토를 끝낸 뒤 마지막 절에서 대조합니다.

### 4. 목표 한 항목을 근거 있는 문장으로 바꿉니다 (S0)

헌장 전체의 완성 예시를 옮겨 쓰기보다 목표 한 항목을 함께 작성합니다. 시작 문장이 “대사 시간을 60분으로 줄인다”라고 되어 있다고 해 보세요. 목표값은 보이지만 누구의 시간인지, 매일 반드시 같은 값이어야 하는지, 언제부터 측정하는지, 누가 확인하는지가 빠져 있습니다. 이 상태로는 운영과 스폰서가 서로 다른 방식으로 성공을 판단할 수 있습니다.

S01은 현재의 최근 20영업일 평균 120분과 목표를 제공합니다. S17은 프로젝트 종료 다음 영업일부터 20영업일 동안 팀의 일별 순수 대사 경과시간을 모으고 평균을 구하며 박다은이 측정한다고 설명합니다. 따라서 목표 문장을 만들 때는 두 문서의 정보를 결합해야 합니다. 학생이 판단할 것은 어떤 정보를 한 문장과 보충 설명으로 배치할지이며 새 수치를 정하는 일이 아닙니다.

| 필요한 요소 | 근거를 읽는 방법 |
|---|---|
| 대상 | 팀의 일별 순수 대사 경과시간인지 확인 |
| 목표 | 평균 60분 이하라는 조건 확인 |
| 기간 | 종료 다음 영업일부터 20영업일 확인 |
| 방법 | 시작·종료·중단 기록으로 순수 경과시간 계산 |
| 책임 | 박다은의 측정·보고 책임 확인 |

부분 수정문은 “프로젝트 종료 다음 영업일부터 20영업일 동안 팀의 일별 순수 대사 경과시간 평균이 60분 이하인지 박다은이 측정한다”로 쓸 수 있습니다. 측정 방법은 별도 문장에 운영일지의 시작·종료·중단 기록을 사용한다고 보완합니다. 이 예시는 목표 정의의 형태를 보여 주며, 미래 목표가 달성됐다는 뜻은 아닙니다.

같은 항목에 “직원 세 명의 시간을 합해 평균 60분”이라고 쓰면 측정 대상을 바꾼 것입니다. S01의 업무시간 재배치 편익은 별도 계산이며 실제 현금 절감 보장이 아닙니다. 목표와 편익을 함께 설명하더라도 어떤 단위를 어떤 이유로 사용하는지 나눠야 합니다. 보기 좋은 효과를 만들기 위해 인원 수를 중복해서 곱하지 않습니다.

이제 예외 이력 목표는 직접 작성합니다. 대상과 확인 조건을 S01·S03에서 찾고 어떤 요구로 이어지는지 표시하세요. 권한 항목도 “PM이 프로젝트를 총괄한다”로 끝내지 말고 업무 배정·정보 요청·변경 상정 중 할 수 있는 행동과, 기준선 변경처럼 스폰서의 결정이 필요한 행동을 구분합니다. 예제의 문장 구조를 사용하되 완성 답안을 복사하는 방식으로 끝내지 않습니다.

### 5. 검토자는 문장 길이보다 빠진 판단 조건을 봅니다 (S0)

아래는 S01·S02·S03·S17을 적용하는 교육용 검토 상황입니다. 회사에서 새로 발생한 회의나 회신을 추가한 것이 아닙니다. 운영·재무·보안·QA·스폰서의 관점을 차례로 적용하며 자신의 D01을 읽어 봅니다. 실제 수업에서는 같은 원천을 가진 동료가 역할을 나눠 의견을 줄 수 있습니다.

운영 관점에서 “평균 60분”만 있는 목표는 측정 기간과 담당을 묻게 합니다. 재무 관점에서 “예산 132백만원 승인 완료”라는 초안은 현재 상태를 묻게 합니다. S17에 따르면 지금의 숫자는 투자 한도이며 상세 원가기준선은 별도 승인 대상입니다. 보안 관점에서는 기존 포털 권한 시험이 신규 화면 개발 약속으로 넓어지지 않았는지 확인합니다.

| 수정 전 표현 | 검토 질문 | 수정 후 담아야 할 뜻 |
|---|---|---|
| 업무를 60분에 처리한다 | 어떤 대상과 기간의 값인가 | 팀 경과시간·평균·측정 기간·담당 |
| 상세 예산을 승인했다 | 지금 어떤 승인 근거가 있는가 | 투자 한도와 상세 기준선 승인 상태 구분 |
| PM이 모든 변경을 결정한다 | S02의 권한 경로와 같은가 | PM 분석·상정, 지정 검토, 스폰서 결정 |
| 개발이 끝나면 종료한다 | 운영과 잔여 책임은 어디로 가는가 | 인수·운영절차·계약·자원·편익 책임 |

의견을 받았으면 항목과 문제를 좁혀 적습니다. “내용 부족”보다 “목표와 측정 항목에 종료 후 측정 기간이 없음”이 바로 수정할 수 있는 의견입니다. 수정 후에는 “문장을 보완했다”가 아니라 어떤 조건을 넣었는지 적습니다. 근거 ID와 수정본의 문단 위치를 연결하면 검토자가 다시 확인하기 쉽습니다.

처리 기록의 한 예는 “목표와 측정 / 측정 기간 누락 / 종료 다음 영업일부터 20영업일을 추가 / S17 / v0.2 해당 문단”입니다. 이 구조는 표현 방법의 예시이며 학생에게 실제 오류가 있었다고 가정하지 않습니다. 이미 맞게 썼으면 충족한 위치와 근거를 기록합니다. 수정 횟수를 채우기 위해 일부러 잘못 쓸 필요는 없습니다.

v0.1을 보존하고 v0.2를 승인 대기로 둡니다. 검토 의견을 모두 처리한 것과 스폰서가 착수를 승인한 것은 다릅니다. 지금까지는 필요한 내용을 준비한 상태입니다. 다음 절의 승인 자료는 수정본의 항목을 대조할 때 사용하며, 승인이 있을 것이라는 예상으로 승인란을 먼저 채우지 않습니다.

### 6. 수정본을 승인 조건과 대조하고 계획의 입력으로 넘깁니다 (S0A)

앞 절의 초안과 검토 기록을 보존한 뒤 S0A의 S16을 엽니다. 이 절은 승인 조건을 대조하는 단계이므로 아직 초안을 작성 중이라면 먼저 돌아가 항목을 채우세요. 승인 원천을 먼저 읽어도 자신의 D01의 빠진 내용을 자동으로 해결하지는 못합니다. 자료를 열었다는 행동과 문서가 조건을 충족한다는 판단을 구분합니다.

S16은 AP00으로 프로젝트 착수와 PM 권한을 승인한 조건을 제공합니다. 목표·범위·제외 항목·총자금 한도·종료 목표·PM 권한뿐 아니라 S17의 측정·포털 경계·종료 조건을 포함합니다. 자신의 v0.2에서 각 조건이 어느 항목에 들어 있는지 하나씩 확인합니다. 일치하지 않으면 해당 문장을 수정하거나 다른 제안으로서 검토할 대상으로 표시하고 임의로 승인됐다고 쓰지 않습니다.

| 승인 대조 대상 | 학생이 확인할 것 |
|---|---|
| 목표 | 수치뿐 아니라 측정 대상·기간·책임이 같은가 |
| 범위 | 요구와 제외 경계가 넓어지거나 빠지지 않았는가 |
| 자금·일정 | 한도와 목표의 상태를 상세 기준선과 구분했는가 |
| 권한 | PM과 검토자·스폰서의 역할이 규정과 같은가 |
| 종료·편익 | 현업 인수와 종료 승인, 사후 측정을 구분했는가 |

조건과 맞는 수정본은 D01 v1.0으로 보관하고 AP00·승인자·시나리오 승인일을 근거에 따라 기록합니다. 이 승인은 상세 범위·일정·원가기준선까지 승인했다는 뜻이 아닙니다. 후속 계획은 여러 전문 자료를 맞춘 뒤 통합 승인 절차로 갑니다. 승인된 헌장에는 사업을 시작할 이유와 권한이 있고, 상세 계획에는 수행 방법과 비교 기준이 들어갑니다.

다음으로 자료를 닫고 목표 하나, 제외 경계 하나, PM이 단독으로 결정할 수 없는 일 하나를 설명해 보세요. 설명에 막히면 문구를 외우기보다 해당 원천과 문서 위치를 다시 찾습니다. D30에는 누구에게 확인할지, A01에는 어떤 전제가 확인됐고 무엇을 나중에 확인할지 남겨 둡니다. 헌장이 승인됐다고 이 두 기록의 관리가 끝나지는 않습니다.

D01의 상위 요구와 경계를 2단원의 D08~D11로 넘깁니다. 이제는 사업의 큰 약속을 요구 문장·인수조건·작업패키지로 더 상세히 설명할 차례입니다. 승인본과 수정 이력을 함께 보관하면 이후 범위가 달라졌을 때 최초에 어떤 목적과 경계를 합의했는지 다시 확인할 수 있습니다.

다음 업무: 승인 조건과 일치하는 헌장, 이해관계자 등록부, 가정 로그와 검토 이력을 요구사항·범위 계획의 입력으로 넘긴다.

## 1. 오늘의 요청과 초안 상태 이해하기

자료 단계: S0. 관련 프로세스: 4.1.

[S01 사업제안과 스폰서 면담](../02_원천문서/S0/S01.md) · [S02 조직·권한·문서 규정](../02_원천문서/S0/S02.md)

### 이번 업무를 이해하기

오늘은 사업을 시작할 이유와 PM 권한을 정리하는 날입니다. 프로젝트코드 MP-01, 작성자 한지우, 회사의 시나리오 날짜와 실제 학습일을 구분합니다. D01을 복사해 v0.1·초안으로 둡니다.

### 개념을 한 단계 더 이해하기

헌장을 읽는 사람은 내용뿐 아니라 그 문서가 어떤 상태인지 보고 행동합니다. 초안을 승인본으로 착각하면 아직 결정하지 않은 예산·일정에 맞춰 일을 시작할 수 있습니다. 문서 ID는 같은 산출물을 식별하고, 버전은 그 산출물의 변화를, 상태는 지금 사용할 수 있는 권한의 범위를 설명합니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S01 → 조회 → 목록의 S01 상세를 엽니다. 읽을 부분: 사업 필요, 현재값·목표값, 투자 한도와 최초 종료 목표. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S02 → 조회 → 목록의 S02 상세를 엽니다. 읽을 부분: 역할별 권한, 문서 검토·승인 및 변경 상정 절차. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S01의 사업 요청과 S02의 권한 규정을 나란히 놓습니다. 요청이 있다는 사실은 헌장을 작성할 이유이고, 승인이 있다는 증거는 별도로 필요합니다. D01 v0.1의 작성자·작성일·상태를 먼저 채우되 시나리오 기준일과 실제 학습일을 나눕니다. 빈 승인란은 누락이 아니라 현재 상태를 정직하게 표시한 것입니다.

### 함께 따라 하는 예제

### 문서에 반영하기

### 검토와 수정

원천 문서의 작성자를 학생 산출물의 승인자로 그대로 옮기지 않았는지 확인합니다.

### 다음 업무로 넘기기

작성한 항목은 D01 초안에 모읍니다. 다음 단계에서는 이 내용을 새로 만들지 않고 같은 버전에서 보완합니다.

## 2. 현재 문제를 사업을 시작할 이유로 연결하기

자료 단계: S0. 관련 프로세스: 4.1.

[S01 사업제안과 스폰서 면담](../02_원천문서/S0/S01.md) · [S05 기존 정산 절차와 과거 교훈](../02_원천문서/S0/S05.md)

### 이번 업무를 이해하기

현재 수작업 대조와 예외 추적 누락이 어떤 문제를 만드는지 읽습니다. 현상, 업무 영향, 개선 이유 순서로 두세 문장을 씁니다. 프로그램 이름보다 개선해야 할 업무를 먼저 설명합니다.

### 개념을 한 단계 더 이해하기

사업 필요는 “새 도구가 있으면 좋겠다”는 선호와 다릅니다. 현재 업무의 어떤 문제 때문에 누구에게 어떤 영향이 생기는지 설명하고, 그 문제를 바꿀 필요가 있는 이유를 연결합니다. 개선 수단을 먼저 확정하면 실제 문제와 무관한 기능을 늘리기 쉽습니다. 헌장에서는 업무 문제를 출발점으로 삼습니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S01 → 조회 → 목록의 S01 상세를 엽니다. 읽을 부분: 사업 필요, 현재값·목표값, 투자 한도와 최초 종료 목표. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S05 → 조회 → 목록의 S05 상세를 엽니다. 읽을 부분: 기존 정산 절차와 LL01~LL03의 교훈. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S01에서 개선 요청의 이유를 찾고 S05에서 그 이유가 나타나는 업무 위치를 확인합니다. 수작업 대조 시간과 예외 추적 문제를 함께 보되 둘을 같은 지표라고 쓰지 않습니다. “빠른 화면”은 수단에 대한 아이디어이고 “확인 시간과 처리 이력 개선”은 관리할 업무 결과에 가깝습니다.

### 함께 따라 하는 예제

“자료 대조에 시간이 걸린다 → 확인 업무와 예외 추적을 일관되게 관리할 필요가 있다 → 기존 거래자료를 사용하는 내부 도구 개선을 제안한다”처럼 연결합니다.

### 문서에 반영하기

D01의 「사업 필요」 항목에 반영합니다. 사실에는 자료 ID와 읽은 부분을, 자신의 판단에는 판단 이유를 붙이세요. 필요한 경우 해당 양식을 내려받아 작성합니다.

### 검토와 수정

“좋은 시스템 구축”이라는 표현만 있다면 현재 문제와 누구의 업무가 달라지는지 보완합니다.

### 다음 업무로 넘기기

작성한 항목은 D01 초안에 모읍니다. 다음 단계에서는 이 내용을 새로 만들지 않고 같은 버전에서 보완합니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

D01의 사업 필요에 현재 상황→업무 영향→개선 목적 순서로 씁니다. 자료에 없는 손실액이나 고객 이탈률을 더해 설득력을 꾸미지 마세요. 뒤에서 목표 수치와 상위 요구를 쓸 때 이 문단의 문제를 실제로 해결하는지 다시 대조합니다.

### 생각을 확인하기

## 3. 함께 일할 사람과 확인받을 일을 정하기

자료 단계: S0. 관련 프로세스: 13.1.

[S01 사업제안과 스폰서 면담](../02_원천문서/S0/S01.md) · [S02 조직·권한·문서 규정](../02_원천문서/S0/S02.md) · [S03 정산 업무 인터뷰와 요구사항 원문](../02_원천문서/S0/S03.md) · [S17 착수 확인 회신: 측정·채널·종료 조건](../02_원천문서/S0/S17.md)

### 이번 업무를 이해하기

사람의 이름을 아는 것과 그 사람에게 어떤 결정을 확인할지 아는 것은 다릅니다. 이해관계자 등록부는 연락처 목록을 넘어 요구·검토·승인·인수 책임을 연결합니다. 영향력에 대한 자신의 판단은 회사가 정한 권한과 구분합니다.

### 개념을 한 단계 더 이해하기

이해관계자(Stakeholder)는 단순히 회의에 참석하는 사람이 아닙니다. 결과에 영향을 주거나 영향을 받는 사람이며, 각자의 관심과 결정권이 다릅니다. 등록부의 권한은 S02의 사실로 적고, 영향력·관심 수준은 근거를 가진 PM의 판단으로 표시합니다. 판단을 회사의 공식 권한처럼 쓰지 않습니다.

### 가져올 문서와 현재 상태

D01초안

### ERP 목록과 문서 연결하기

ERP에서 「조직·담당자」 → 「초기화」 → 정확히 일치 항목 「person_id」 → 값 「P03」 → 「조회」 순서로 진행합니다.

name은 이름, authority는 확인 권한, interest는 관심사입니다. P03의 권한을 D30에 옮기고, P04를 직접 찾아 비용 검토 역할을 추가합니다.

조회 결과가 다르면 현재 자료 단계와 남은 검색조건을 먼저 확인하세요. 원천 ERP는 읽기 전용이며 작성은 내려받은 문서에서 합니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S01 → 조회 → 목록의 S01 상세를 엽니다. 읽을 부분: 사업 필요, 현재값·목표값, 투자 한도와 최초 종료 목표. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S02 → 조회 → 목록의 S02 상세를 엽니다. 읽을 부분: 역할별 권한, 문서 검토·승인 및 변경 상정 절차. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

3. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S03 → 조회 → 목록의 S03 상세를 엽니다. 읽을 부분: 박다은·김소연·오수빈의 발언, R01~R05의 인수조건과 제외 범위. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

4. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S17 → 조회 → 목록의 S17 상세를 엽니다. 읽을 부분: 목표 측정 기간·담당, 기존 포털 경계, 자금·가정·종료 조건. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

박다은의 요구와 인수 역할을 확인한 뒤, QA·보안·스폰서가 각각 무엇을 검토하는지 나눠 보세요. “승인”이라는 단어 하나로 합치면 기능의 수락, 보안 확인, 사업 결정이 사라집니다. 계약 전 공급자 후보도 관련자는 될 수 있지만 이미 선정된 회사의 확정 책임자로 다루지 않습니다.

### 함께 따라 하는 예제

박다은 P03의 역할은 정산 운영책임자이고 업무 요구와 인수를 확인합니다. D30에 “업무 요구·인수조건 확인, 운영 시연 참여”를 연결합니다. 정유나의 QA 검증이나 윤서진의 종료 승인을 대신하는 역할로 쓰지 않습니다.

### 문서에 반영하기

D30 이해관계자등록부 양식을 사용합니다.

1. 회사 인물표의 열 명을 D30에 옮기고 회사 내부·외부를 구분한다.

2. 문서별 작성·검토·승인·인수 권한을 S02에서 찾아 역할 옆에 기록한다. 아직 계약 전인 공급사는 후보 역할로 표시한다.

3. 영향력·관심은 근거와 자신의 판단을 구분하고 각 사람에게 언제 무엇을 확인받을지 한 가지씩 적는다.

### 직접 확인해 보기

최민석과 오수빈을 인물 상세에서 찾아 각자에게 확인할 질문을 하나씩 정하세요. 아직 계약 전인 외주 책임자는 공급자 후보 역할임을 표시합니다.

### 검토 의견으로 수정하기

초안 “박다은: 모든 결과 승인” → 업무 인수와 사업 승인이 섞였습니다 → “업무 요구·운영 인수 확인; 프로젝트 종료는 윤서진 승인”으로 분리합니다.

검토 역할: 박다은. 박다은의 업무 인수, 정유나의 품질 검증, 윤서진의 종료 승인을 같은 승인으로 합치지 않았나요? 문서별 책임을 나누세요. 이미 충족한 경우 문장의 근거를 확인하면 됩니다. 오류를 일부러 만들 필요는 없습니다.

### 다음 업무로 넘기기

D30 이해관계자등록부의 현재 버전과 근거를 보존합니다. 이 문서를 다시 사용할 때 현재 상태가 초안·분야 검토·승인 중 무엇인지 확인합니다. 문서 본문은 한 번 작성하고 수행표에는 위치만 남깁니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

D30의 각 행에 다음 접점 하나를 붙입니다. 누구에게 어떤 자료를 보여 주고 무엇을 확인받을지 적으면 이후 D23의 의사소통과 D31의 참여 활동으로 옮길 수 있습니다. 이름·직함만 채운 표보다 결정과 질문이 연결된 등록부가 실제 PM 업무에 유용합니다.

### 다음에 이어 할 일

목표를 측정 가능한 문장으로 만들기 단계로 이어집니다. 현재 작성한 문서의 항목·근거를 가져가세요. 자료 단계가 바뀌면 먼저 현재 기록을 보존합니다.

### 생각을 확인하기

PM이 판단한 영향력 수준과 회사가 정한 승인권한은?

1. 서로 다른 정보이므로 근거와 성격을 나누어 기록한다.
2. 영향력이 높으면 모든 승인권한을 갖는다.
3. 승인권한만 있으면 관심사는 기록할 필요 없다.

먼저 선택한 이유를 자신의 말로 설명해 보세요.

자기확인 해설: 1번. 영향력 평가는 참여 전략을 돕는 판단이고, 승인권한은 규정에 근거한 권한입니다. 둘을 섞으면 잘못된 승인 경로를 만들 수 있습니다.

## 4. 목표를 측정 가능한 문장으로 만들기

자료 단계: S0. 관련 프로세스: 4.1.

### 이번 업무를 이해하기

헌장은 상세 계획을 모두 아는 사람이 쓰는 마지막 보고서가 아닙니다. 스폰서가 시작을 결정하고 PM에게 일을 맡길 수 있도록 목적·경계·권한을 묶는 문서입니다. 사실은 회사 자료에서 가져오고, 아직 확인하지 않은 상세 계획은 다음 확인 시점을 남깁니다.

### 개념을 한 단계 더 이해하기

목표에는 결과 수치만 아니라 측정 대상·방법·기간·책임이 필요합니다. “시간을 반으로 줄인다”는 표현에서 팀의 경과시간인지 개인별 공수인지가 빠지면 같은 개선을 다르게 계산하게 됩니다. 목표는 앞으로 확인할 성공 조건이며 현재 실적을 보고하는 문장과 시제가 다릅니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S01 → 조회 → 목록의 S01 상세를 엽니다. 읽을 부분: 사업 필요, 현재값·목표값, 투자 한도와 최초 종료 목표. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S17 → 조회 → 목록의 S17 상세를 엽니다. 읽을 부분: 목표 측정 기간·담당, 기존 포털 경계, 자금·가정·종료 조건. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S01의 현재값·목표값을 S17의 측정 정의와 묶어 읽습니다. 분 단위의 업무 경과시간과 편익 산정에 쓰는 사람 시간을 구분하세요. 평균은 관찰 기간의 값을 모아 계산하는 지표이므로 하루의 값만 보고 달성이라고 결론낼 수 없습니다. 지금은 측정 계획을 문장으로 만드는 단계입니다.

### 함께 따라 하는 예제

S01의 현재 120분·목표 60분에 S17의 측정 조건을 붙입니다. “종료 다음 영업일부터 20영업일 동안 팀의 일별 순대사 경과시간 평균이 60분 이하인지 박다은이 측정한다”라고 쓰면 대상·목표·기간·책임이 연결됩니다. 이것은 목표의 정의이며 이미 달성했다는 보고가 아닙니다.

### 문서에 반영하기

D01의 「목표와 측정」 항목에 반영합니다. 사실에는 자료 ID와 읽은 부분을, 자신의 판단에는 판단 이유를 붙이세요. 필요한 경우 해당 양식을 내려받아 작성합니다.

### 검토와 수정

“60분으로 줄인다”만 있으면 박다은은 언제부터 얼마나 측정할지 알 수 없습니다. 측정 대상·기간·책임을 덧붙이고 미래 효과를 달성으로 쓰지 않습니다.

### 다음 업무로 넘기기

작성한 항목은 D01 초안에 모읍니다. 다음 단계에서는 이 내용을 새로 만들지 않고 같은 버전에서 보완합니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

D01 목표 문장을 담당자에게 읽어 준다고 생각해 보세요. 누가 언제부터 어떤 기록을 모아 무엇과 비교할지 알 수 있어야 합니다. 시간 목표의 문장 구조를 참고해 예외 이력 목표도 직접 작성하고, 세부 검사 설계는 요구·품질 단원으로 넘깁니다.

상위 요구와 인수의 뜻 이해하기 단계로 이어집니다. 현재 작성한 문서의 항목·근거를 가져가세요. 자료 단계가 바뀌면 먼저 현재 기록을 보존합니다.

### 생각을 확인하기

하루 측정값이 목표 이내이면 장기 평균 목표 달성을 확정할 수 있나요?

1. 목표보다 낮으면 언제나 확정한다.
2. 운영자가 원하면 측정 기간을 생략한다.

먼저 선택한 이유를 자신의 말로 설명해 보세요.

## 5. 상위 요구와 인수의 뜻 이해하기

자료 단계: S0. 관련 프로세스: 4.1.

[S03 정산 업무 인터뷰와 요구사항 원문](../02_원천문서/S0/S03.md)

### 이번 업무를 이해하기

헌장에는 제공할 핵심 기능과 받아들일 조건을 요약합니다. 활동별 시험 순서는 다음 계획에서 상세화합니다. 정산 계산 정확성과 대사 분류 정확성은 서로 다른 조건입니다.

### 개념을 한 단계 더 이해하기

상위 요구는 어떤 가치를 제공할지 요약하고, 인수조건은 그 약속을 받아들일 수 있는 기준을 제시합니다. 헌장에서 세부 테스트 절차까지 모두 설계할 필요는 없지만, “정확하게 처리”처럼 해석이 갈리는 말을 그대로 두어서도 안 됩니다. 인터뷰의 목적과 조건을 함께 압축해야 합니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S03 → 조회 → 목록의 S03 상세를 엽니다. 읽을 부분: 박다은·김소연·오수빈의 발언, R01~R05의 인수조건과 제외 범위. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S03의 각 요구를 읽으며 기능 동사와 합격 조건을 다른 색으로 표시한다고 생각해 보세요. 조회·분류·이력 관리·권한·운영 수행은 서로 다른 결과를 확인합니다. 대사가 정확하다는 말은 실제 불일치를 정확히 분류하는 뜻이며, 원천의 차이를 없앤다는 뜻으로 바꿀 수 없습니다.

### 함께 따라 하는 예제

대사에서는 실제 금액 차이가 있어도 그것을 불일치로 정확히 찾아야 합니다. “모든 거래를 일치로 만든다”는 목표로 바꾸면 안 됩니다.

### 문서에 반영하기

### 검토와 수정

R01~R05를 요약하되 상세 시험 결과나 아직 수행하지 않은 통과율을 기록하지 않습니다.

### 다음 업무로 넘기기

작성한 항목은 D01 초안에 모읍니다. 다음 단계에서는 이 내용을 새로 만들지 않고 같은 버전에서 보완합니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

D01에는 상위 결과와 확인 책임을 요약하고 상세 요구 ID를 남깁니다. 이후 D09에서 같은 요구를 시험과 연결할 때 뜻이 바뀌지 않아야 합니다. 지금 존재하지 않는 시험 통과 결과를 적는 대신 무엇을 검증해야 하는지 미래 조건으로 작성하세요.

### 다음에 이어 할 일

### 근거를 판단으로 바꾸는 과정

## 8. 지금 알 수 있는 주요 일정만 적기

자료 단계: S0. 관련 프로세스: 4.1.

[S01 사업제안과 스폰서 면담](../02_원천문서/S0/S01.md)

### 이번 업무를 이해하기

착수 시점에는 종료 목표와 계획·구현·검증·이관의 순서를 설명합니다. 상세 A~G 날짜는 기술 추정과 자원 검토를 한 뒤 일정 단원에서 계산합니다.

### 개념을 한 단계 더 이해하기

초기 목표일과 계산된 일정은 목적이 다릅니다. 목표일은 사업이 원하는 제약을, 상세 일정은 활동·관계·자원이 그 목표를 충족할 수 있는지를 보여 줍니다. 헌장에 목표를 적는다고 실행 가능성이 검증된 것은 아닙니다. PM은 둘 사이의 검토가 필요하다는 상태를 분명히 합니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S01 → 조회 → 목록의 S01 상세를 엽니다. 읽을 부분: 사업 필요, 현재값·목표값, 투자 한도와 최초 종료 목표. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S01에서 지금 알려진 주요 시점을 찾고, 아직 근거가 없는 활동별 날짜를 구분합니다. 이후 일정 단원에서 작업 순서와 기간을 계산할 예정이라고 기록하세요. 화면에 미래 정보가 보이더라도 현재 자료의 근거 없이 착수 당시 확정 사실로 소급해서 쓰지 않습니다.

### 함께 따라 하는 예제

S01의 최초 종료 목표를 표시하고 상세 일정은 계획 수립 시 확정 예정이라고 적습니다. 이미 후속 단원을 읽었더라도 미래 기준선을 초안에 복사하지 않습니다.

### 문서에 반영하기

D01의 「주요 일정」 항목에 반영합니다. 사실에는 자료 ID와 읽은 부분을, 자신의 판단에는 판단 이유를 붙이세요. 필요한 경우 해당 양식을 내려받아 작성합니다.

### 검토와 수정

초안에 활동별 확정 날짜가 있다면 착수 당시의 근거가 있는지 확인하고 없는 날짜는 계획 수립 대상으로 돌립니다.

### 다음 업무로 넘기기

1. 아니요, 활동·선후 관계·자원으로 실행 가능성을 검토해야 한다.
2. 예, 목표일이 있으므로 계산이 필요 없다.
3. 예, 목표일을 넘는 활동은 기록에서 삭제한다.

먼저 선택한 이유를 자신의 말로 설명해 보세요.

## 9. PM이 결정할 일과 상정할 일 나누기

### 이번 업무를 이해하기

### 근거를 판단으로 바꾸는 과정

S02에서 일상 조정과 승인 대상 결정을 각각 표시하세요. 한 가지 요청을 받았다고 가정할 때 PM이 할 수 있는 “접수·영향 분석·검토 요청”과 승인권자가 할 “결정”을 화살표로 그려 봅니다. 이 경로를 헌장에 적으면 후속 변경 시 같은 규칙을 다시 사용할 수 있습니다.

### 다음 업무로 넘기기

## 10. 가정·제약·위험과 종료 책임 정리하기

### 이번 업무를 이해하기

가정은 계획의 전제로 확인할 내용, 제약은 지켜야 할 경계, 위험은 아직 발생하지 않은 사건입니다. A01 가정 로그에서 확인 책임·시점·결과를 남깁니다. 종료 후에도 운영과 편익 책임은 이어집니다.

### 개념을 한 단계 더 이해하기

가정은 계획을 세울 때 참이라고 두는 전제이고, 제약은 지켜야 할 경계이며, 위험은 불확실한 사건이 목표에 영향을 줄 가능성입니다. 세 개를 모두 “주의할 일”로 묶으면 누가 언제 확인해야 하는지 사라집니다. 가정이 확인되면 상태를 갱신하고, 틀린 가정의 영향은 계획이나 위험 기록으로 연결합니다.

### 자료를 찾아 읽기

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S17 → 조회 → 목록의 S17 상세를 엽니다. 읽을 부분: 목표 측정 기간·담당, 기존 포털 경계, 자금·가정·종료 조건. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

S17의 기존 거래자료 사용 가능 조건을 읽고 A01에 확인 내용·책임·현재 근거를 남겨 보세요. 아직 모르는 구체적인 인원·환경 일정을 추측해서 추가하지 않습니다. 종료 조건도 개발 완료만 보는지, 현업 사용·운영 인계·잔여 책임까지 보는지 S05의 교훈과 대조합니다.

### 함께 따라 하는 예제

3. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S03 → 조회 → 목록의 S03 상세를 엽니다. 읽을 부분: 박다은·김소연·오수빈의 발언, R01~R05의 인수조건과 제외 범위. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

4. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S17 → 조회 → 목록의 S17 상세를 엽니다. 읽을 부분: 목표 측정 기간·담당, 기존 포털 경계, 자금·가정·종료 조건. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 근거를 판단으로 바꾸는 과정

먼저 자기 초안의 항목을 역할별 관점으로 읽습니다. 운영에는 목표·인수, 재무에는 자금 성격, 보안에는 경계, QA에는 검사 조건이 중요합니다. S17의 조건과 다른 문장이 있으면 원천과 대조해 수정 이유를 씁니다. 의견을 처리했다고 스폰서 승인까지 완료된 것은 아닙니다.

### 함께 따라 하는 예제

목표에 기간이 빠졌다면 수정 이력에 “목표와 측정 / 기간 누락 → 종료 후 20영업일 추가 / S17 / 박다은 확인”으로 남깁니다. v0.1은 보존하고 v0.2는 승인 대기로 둡니다.

### 문서에 반영하기

D01의 「검토·승인 이력」 항목에 반영합니다. 사실에는 자료 ID와 읽은 부분을, 자신의 판단에는 판단 이유를 붙이세요. 필요한 경우 해당 양식을 내려받아 작성합니다.

### 검토와 수정

RV01~RV06을 하나씩 대조합니다. 이미 충족했다면 근거 위치를 남기고 닫습니다. 브라우저 입력이나 형식적인 수정 횟수로 통과를 판단하지 않습니다.

### 다음 업무로 넘기기

작성한 항목은 D01 초안에 모읍니다. 다음 단계에서는 이 내용을 새로 만들지 않고 같은 버전에서 보완합니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

의견별로 위치·문제·조치·근거·확인 상태를 남기고 v0.1을 보존합니다. v0.2를 검토자에게 보여 준다고 생각해 “어떤 조건이 어떻게 보완됐는가”를 한 문장으로 설명하세요. 다음 단계에 넘길 것은 수정본과 의견 처리 기록이며 승인 결과는 그 다음에 대조합니다.

### 다음에 이어 할 일

수정본을 승인 조건과 대조하고 다음 단원에 넘기기 단계로 이어집니다. 현재 작성한 문서의 항목·근거를 가져가세요. 자료 단계가 바뀌면 먼저 현재 기록을 보존합니다.

### 생각을 확인하기

모든 검토 의견을 처리한 v0.2의 적절한 다음 상태는?

1. 검토 완료 또는 승인 대기
2. 자동 승인 완료
3. 모든 상세 계획 기준선 승인 완료

먼저 선택한 이유를 자신의 말로 설명해 보세요.

자기확인 해설: 1번. 내용 검토와 착수 승인은 다른 결정입니다. 의견 처리 기록을 갖춰 다음 승인 단계에서 조건을 확인합니다.

## 12. 수정본을 승인 조건과 대조하고 다음 단원에 넘기기

자료 단계: S0A. 관련 프로세스: 4.1.

[S16 헌장 검토·승인 회신 AP00](../02_원천문서/S0A/S16.md) · [S17 착수 확인 회신: 측정·채널·종료 조건](../02_원천문서/S0/S17.md)

### 승인 자료를 읽기 전에

D01 v0.2와 의견 처리 기록을 보존한 뒤 S0A 자료팩을 엽니다. 자료를 열었다는 사실만으로 학생 문서가 승인된 것은 아닙니다.

### 개념을 한 단계 더 이해하기

승인은 버튼을 눌렀다는 사실보다 어떤 버전의 어떤 조건을 결정했는지가 중요합니다. 학습용 승인 원천은 검토 기준을 제공하지만 학생 문서의 빈칸이나 모순을 자동으로 해결하지 않습니다. 본인이 만든 수정본이 그 조건을 충족하는지 대조해야 승인 근거를 사용할 수 있습니다.

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S16 → 조회 → 목록의 S16 상세를 엽니다. 읽을 부분: 헌장의 수정 조건과 AP00 승인 기록. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S17 → 조회 → 목록의 S17 상세를 엽니다. 읽을 부분: 목표 측정 기간·담당, 기존 포털 경계, 자금·가정·종료 조건. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 승인 조건 대조

목표·경계·자금 상태·권한·종료 및 편익 책임을 S16과 항목별로 비교합니다. 일치하면 D01 v1.0에 AP00·윤서진·2026-10-08을 교육용 승인 근거로 기록합니다. 다르면 해당 항목을 수정합니다.

### 근거를 판단으로 바꾸는 과정

S16과 S17을 읽으며 목표·범위·자금 상태·권한·종료 책임을 D01의 해당 위치에 연결합니다. 다르면 회사 자료에 맞춰 문서를 수정하고, 같은 경우에는 충족한 문단을 확인합니다. 승인이 헌장에 관한 결정인지 상세 일정·원가기준선까지 확정한 결정인지 범위를 구분하세요.

### 다음 업무로 넘기기

D01의 목적과 범위 경계는 D08~D11로, D30의 검토 역할은 참여·자원계획으로, A01의 미확인 항목은 계획 단계 확인으로 넘깁니다. 헌장 승인과 상세 범위·일정·원가 기준선 승인은 구분합니다.

### 내 문서에 적용하고 다음 사람에게 넘기기

D01 v1.0과 검토 이력을 함께 보관합니다. D08~D11 작성자는 이 문서의 목적·경계·상위 조건을 가져가고, D30·A01은 계획 수립 중에도 갱신합니다. 승인본을 수정할 때 원본을 덮어쓰지 않는 습관이 이후 기준선 변경관리의 기초가 됩니다.

### 단원 마무리

D01 초안·근거표, D30, A01 가정 로그, 검토 및 수정 기록을 제출합니다. 수정 완료 후 S0A의 S16/AP00을 확인하고 조건이 일치하는 D01을 v1.0으로 보관합니다. 이 승인본의 목표·경계·권한을 다음 단원에 인계합니다.

### 생각을 확인하기

S16을 열었지만 내 헌장의 목표 측정 조건이 빠져 있습니다. 올바른 행동은?

1. 승인 자료를 열었으니 그대로 승인본으로 둔다.
2. 빠진 조건을 보완하고 일치 여부를 확인한 뒤 승인 근거를 기록한다.
3. 원천 승인 조건을 내 초안에 맞게 수정한다.

먼저 선택한 이유를 자신의 말로 설명해 보세요.

자기확인 해설: 2번. 교육용 승인 원천도 학생 산출물의 타당성을 대신하지 않습니다. 먼저 문서와 승인 조건을 대조해야 합니다.

# 02. 요구사항과 범위

박다은은 원하는 기능을 설명했지만 개발팀은 구현 경계와 합격 조건이 필요합니다. 같은 말을 서로 다르게 해석하지 않도록 요구와 범위를 연결해 주세요.

요구사항(Requirement)은 사용자가 필요로 하는 것, 범위(Scope)는 이번 프로젝트에서 제공하기로 한 결과와 작업의 경계입니다. WBS는 그 범위를 인도물 중심으로 빠짐없이 나눈 구조입니다. “교육 실시”라는 활동만 적는 대신 교육자료·운영 시연 확인처럼 남아야 할 결과를 생각합니다. 추적표는 요구가 어느 작업과 시험으로 이어지는지 보여 줍니다. 포함되지 않는 일도 명시해야 추가 요청을 판단할 수 있습니다.

이 단원은 설명 → 자료 조회 → 예제 → 직접 확인 → 검토·수정 → 다음 업무 순서로 진행합니다. 웹 입력은 필요하지 않습니다. 문서를 작성할 때는 양식을 내려받고 같은 문서의 버전을 이어 갑니다.

## 1. 요구를 접수하고 판단하는 절차 정하기

자료 단계: S1. 관련 프로세스: 5.1.

### 이번 업무를 이해하기

누군가 기능을 요청할 때마다 곧바로 개발하면 범위가 계속 늘어납니다. 먼저 누가 요청을 기록하고, 뜻을 확인하고, 시험과 인수를 판단하는지 정합니다. D08은 기능 목록이 아니라 그 목록을 관리하는 방법입니다.

### 가져올 문서와 현재 상태

D01

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S02 → 조회 → 목록의 S02 상세를 엽니다. 읽을 부분: 역할별 권한, 문서 검토·승인 및 변경 상정 절차. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S03 → 조회 → 목록의 S03 상세를 엽니다. 읽을 부분: 박다은·김소연·오수빈의 발언, R01~R05의 인수조건과 제외 범위. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

3. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S18 → 조회 → 목록의 S18 상세를 엽니다. 읽을 부분: 패키지 인도물·담당과 T01~T05 시험 설계. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 함께 따라 하는 예제

“요구 접수: PM이 요청자·내용·이유를 D09에 등록 → 박다은이 업무 뜻 확인 → 개발·QA가 구현·시험 가능성 검토”처럼 적습니다. 승인 후 새 요구가 오면 기존 범위를 바로 덮어쓰지 않고 변경요청으로 접수합니다.

### 문서에 반영하기

D08 범위·요구사항 관리계획 양식을 사용합니다.

1. D08에 요구 접수→내용 확인→범위 정의→시험→현업 인수→변경 순서를 적는다.

2. 각 단계에 S02/S18의 책임자·기록·판정조건을 붙인다.

3. 범위 기준선의 구성 문서와 통합 승인 시점을 적고 승인 후 변경은 CR로 접수하도록 정한다.

### 직접 확인해 보기

S02와 S18을 읽고 시험 판정과 현업 인수 단계의 담당·기록을 D08에 추가하세요. 기준선 승인은 7단원에 있음을 표시합니다.

### 검토 의견으로 수정하기

초안 “QA 통과 시 범위 승인” → QA는 시험 증거를 판단합니다 → “QA 검증 후 박다은 인수, 범위 기준선은 통합 승인”으로 나눕니다.

검토 역할: 박다은. QA가 시험에 통과시킨 것을 현업 인수라고 적었다면 검증 담당과 인수 담당을 분리하세요. 이미 충족한 경우 문장의 근거를 확인하면 됩니다. 오류를 일부러 만들 필요는 없습니다.

### 다음 업무로 넘기기

D08 범위·요구사항 관리계획의 현재 버전과 근거를 보존합니다. 이 문서를 다시 사용할 때 현재 상태가 초안·분야 검토·승인 중 무엇인지 확인합니다. 문서 본문은 한 번 작성하고 수행표에는 위치만 남깁니다.

### 다음에 이어 할 일

조회 결과가 다르면 현재 자료 단계와 남은 검색조건을 먼저 확인하세요. 원천 ERP는 읽기 전용이며 작성은 내려받은 문서에서 합니다.

2. D09에 R01~R05별 요구자, 조건, 확인 방법, S18 시험 설계 ID를 한 행씩 작성한다.

3. 가맹점 접근은 S17의 기존 포털 회귀시험 경계로 설명하고 박다은·오수빈에게 해석 확인을 남긴다.

### 직접 확인해 보기

## 4. 산출물을 작업패키지로 나누기

자료 단계: S1. 관련 프로세스: 5.4.

[S03 정산 업무 인터뷰와 요구사항 원문](../02_원천문서/S0/S03.md) · [S06 기술 추정과 활동·자원 자료](../02_원천문서/S1/S06.md) · [S18 범위 분해와 시험 설계 협의 기록](../02_원천문서/S1/S18.md)

### 이번 업무를 이해하기

WBS는 부서별 할 일 목록이 아니라 인도해야 할 결과를 나눈 구조입니다. 완료조건이 있어야 누가 무엇을 끝냈다고 보고하는지 알 수 있습니다. 활동 이름과 패키지는 항상 하나씩 대응하지 않습니다.

### 가져올 문서와 현재 상태

D09,D10

### 자료를 찾아 읽기

1. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S03 → 조회 → 목록의 S03 상세를 엽니다. 읽을 부분: 박다은·김소연·오수빈의 발언, R01~R05의 인수조건과 제외 범위. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

2. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S06 → 조회 → 목록의 S06 상세를 엽니다. 읽을 부분: A~G 기간·선행, WBS, 인력·단가, 월별 비용 배분. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

3. ERP의 원천 문서 메뉴에서 초기화 → 검색어 S18 → 조회 → 목록의 S18 상세를 엽니다. 읽을 부분: 패키지 인도물·담당과 T01~T05 시험 설계. 확인한 사실의 단위·날짜·담당자를 함께 읽습니다.

찾지 못하면 현재 자료 단계와 이전 검색조건을 확인하세요. 파일로 읽을 때는 같은 ID의 원천 문서를 사용합니다. SQL은 선택 경로입니다.

### 함께 따라 하는 예제

WBS 1.1 요구·설계에는 A 요구정의와 B 설계가 함께 들어갑니다. 인도물은 명세·인터페이스·화면과 권한 설계·검토 기록입니다. “A 완료, B 완료”만 쓰지 말고 S18의 인도물을 D11 사전에 적습니다.

### 문서에 반영하기

D11 WBS·사전 양식을 사용합니다.

1. S18의 인도물을 S06의 상위 WBS 코드로 묶고 D11에 패키지별 경계를 적는다.

2. 패키지별 담당 역할·완료 증거·포함 활동을 작성한다. 같은 개발 작업을 검증 패키지 비용에 중복 배정하지 않는다.

3. D09의 모든 요구를 WBS와 연결하고 공통 지원 패키지에는 왜 필요한지 설명한다.

### 직접 확인해 보기

1.3 대사·예외 패키지의 경계·인도물·담당 역할을 작성하세요. 전체 요구가 연결되는지 확인하고 공통 요구·설계 패키지를 빠뜨리지 않습니다. 작업예산은 4단원 추정 후 확정할 후보 값입니다.

### 검토 의견으로 수정하기

초안 “검증 패키지에도 개발비 포함” → 같은 작업비가 중복됩니다 → 구현은 개발 패키지, 검증은 시험 증거와 판정 업무로 경계를 나눕니다.

검토 역할: 이현우. WBS가 A~G 활동명만 나열한 표인가요? 인도물·완료조건을 보완하고 1.1에 A와 B가 함께 속하는 이유를 설명하세요. 이미 충족한 경우 문장의 근거를 확인하면 됩니다. 오류를 일부러 만들 필요는 없습니다.
